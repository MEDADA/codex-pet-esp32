# 动画异步解码开发计划

本轮依据架构评审 §8.4。现有 IDLE 的 LVGL 定时器和互动、THINKING 的显示更新直接解码，后两种还在持显示锁时访问 SPIFFS。上一版工作动画热读盘约 4.6 ms，JPEG 解码约 19.6 ms，并有 4 次锁超时。

- [x] 增加主机回归，覆盖跨场景的旧帧丢弃、双缓冲后备选择、循环换帧以及单次播放结束。
- [x] 用一个低优先级任务串行完成 JPEG 和 SPIFFS，LVGL 定时器非阻塞接收并发布已解码帧。保留当前帧直到下一帧就绪，状态切换作废在途帧。保留原分辨率、素材、帧时序和四行内部 DMA 缓冲。表盘状态采集在现有任务运行，LVGL 定时器从长度为一的队列取最新快照。
- [x] 运行主机测试并构建，保存上一版板载应用后仅写入应用分区。
- [x] 采集实机日志，对照 IDLE、THINKING、解码和刷新统计，记录锁超时、内存及目视验证范围。

## 实施记录

后台任务独占 SPIFFS 和 JPEG 解码器。每次只允许一帧在途，LVGL 只在到达帧时序后切换到已完成的后备缓冲，并按代次丢弃旧场景的结果。两块 RGB565 缓冲从 PSRAM 分配，错误时保留静态图回退。

首次试烧仅迁移解码，85 秒内记录了 111 次 LVGL 锁超时。画面仍有持续刷新，超时来自外部 UI 任务尝试在连续刷屏期间拿锁。第二版将状态快照交由 LVGL 自己更新，BLE、按钮和传感器采集继续在原任务执行。主机回归和构建通过。烧录前用板上镜像哈希核对了回退文件 `device-backup/pre-async-app.bin`，两次写入均限于应用分区。

第二版 70 秒串口采样无 LVGL 锁超时，但工作动画的 JPEG 单帧墙钟耗时为 35.6–44.9 ms，个别帧超过 100 ms。第三版对照将 LVGL 固定在核心 1，低优先级解码任务固定在核心 0，NimBLE 可优先运行。同时把帧调度时钟扩为 64 位，避免同一段循环动画连续运行约 49 天后因毫秒计数回卷而停更。

## 最终上板结果

第三版 4,794,800 B，应用分区仍余 43%。板上启动 ELF SHA256 前缀 `820118d3d` 与构建一致。65 秒采样确认 IDLE 动画启动、CodeIsland 自动重连、时钟同步、切入 THINKING 后播放约 59 秒。无 LVGL 锁超时、SPI/DMA 错误、JPEG 解码错误或重启。

| 实测项目 | 上轮同步版 | 本轮异步分核版 |
| --- | --- | --- |
| 显示锁超时 | 50 秒内 4 次 | 65 秒内 0 次 |
| THINKING 稳态 LVGL 渲染区域更新 | 约 79 次／10 秒 | 约 80 次／10 秒 |
| THINKING 单帧 JPEG 平均墙钟耗时 | 约 19.6 ms，持显示锁 | 约 25.2 ms，后台执行 |
| 内部堆低水位 | 90,559 B | 83,947 B |

首次进入 THINKING 后约 0.9 秒开始播放 JPEG 动画，首段有一次长渲染，稳态均值约 104 ms。渲染区域更新次数不等于面板 FPS。屏幕撕裂、触摸和倾斜的体感还需目视确认。实机数据见 `async-decode-pinned-serial.log`。
